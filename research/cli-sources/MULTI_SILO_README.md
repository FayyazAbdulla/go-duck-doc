# GO-DUCK Multi-Silo Multi-Tenancy Developer Guide

This document describes how to interact with the multi-tenant multi-silo database system generated by GO-DUCK CLI.

---

## 🦆 Core Architectural Principles

GO-DUCK implements a **Database-per-Tenant** architecture using a Triple-Identity Registry to secure physical database paths:
1. **Identity Layer**: Keycloak Realm Role (e.g. `ROLE_HARBOUR_B`).
2. **Opaque Layer**: A randomly generated UUID (`tenantId`) exposed to the client to prevent ID enumeration.
3. **Physical Layer**: The actual database name (e.g. `harbour_b`) masked from the public eye.

---

## 🚀 Methods to Interact with Multi-Tenant Silos

### 1. Implicit Automatic Routing (JWT-Based)
If a user is logged into Keycloak and has roles mapped in the registry, their requests are automatically routed without specifying any headers:
* **How it works**: The `TenantMiddleware` extracts Keycloak roles from the bearer token, resolves them against `tenant_roles`, and binds the connection of the highest-priority role to the request context.
* **Priority Rule**: Dedicated tenant roles (e.g., `role_harbour_b`) are automatically sorted and prioritized over generic ones like `offline_access` to ensure the correct primary connection is resolved.

### 2. Explicit Precision Targeting (`X-Tenant-ID` Header)
If a user has access to multiple silos (e.g., managing both `harbour_a` and `harbour_b`), they can manually choose which silo to target.

1. **Discover Authorized Silos**:
   Retrieve the list of silos and their opaque UUIDs:
   ```bash
   GET /api/silos/me
   Authorization: Bearer <JWT_TOKEN>
   ```
   **Response Example**:
   ```json
   [
     {
       "tenantId": "c2405520-499f-4dba-ade5-a0df39954a84",
       "roleName": "role_harbour_b",
       "dbName": "harbour_b",
       "isPrimary": true
     },
     {
       "tenantId": "test-uuid",
       "roleName": "offline_access",
       "dbName": "harbour_a",
       "isPrimary": true
     }
   ]
   ```

2. **Send Request with Targeting Header**:
   Include the `X-Tenant-ID` header set to the opaque `tenantId` UUID:
   ```bash
   POST /api/institutes
   Authorization: Bearer <JWT_TOKEN>
   X-Tenant-ID: c2405520-499f-4dba-ade5-a0df39954a84
   Content-Type: application/json

   {
     "Name": "Ocean Lanka",
     "Code": "PV-123-1",
     "Address": "Sample Address",
     "ContactNumber": "Sample ContactNumber",
     "Status": "Sample Status"
   }
   ```
   The request is guaranteed to execute against `harbour_b`.

### 3. Parallel Read Harvesting (`?federated=true`)
For GDL entities marked with `@Federated`, you can aggregate reads from all silos you have access to in parallel:
* **How it works**: Query with the query parameter `federated=true`:
  ```bash
  GET /api/institutes?federated=true
  Authorization: Bearer <JWT_TOKEN>
  ```
* **Response format**: Combines results from all accessible silos into a single map grouped by role name:
  ```json
  {
    "offline_access": [
      { "id": 2, "name": "TEST", "code": "1122" }
    ],
    "role_harbour_b": []
  }
  ```

### 4. Cross-Silo Transactional Outbox (Saga Consistency)
For `@Federated` entities, write mutations (CREATE, UPDATE, DELETE) automatically replicate data eventually across every silo you own:
* **How it works**: Writing to your primary silo (e.g. `harbour_b` using either Method 1 or 2) inserts the record synchronously. Simultaneously, transactional outbox records targeting your other silos (e.g. `harbour_a`) are queued.
* **Background Sync**: The `OutboxWorker` reads pending items from the outbox and replays them on target databases asynchronously, using an idempotent `OnConflict: DoNothing` strategy to ensure consistency across the network.

## 📚 Writing to Multiple Databases in One Request

The GO‑DUCK generator already supports federated writes. Follow these steps:

1. **Mark the entity as federated** in your GDL file
   ```gdl
   @Federated
   entity Harbour { … }
   ```
   Run the CLI (`go-duck-cli import‑gdl …`) so the controller uses the outbox.

2. **Assign the user multiple tenant roles** (e.g. `ROLE_HARBOUR_A` and `ROLE_HARBOUR_B`) via the admin endpoint `/management/tenant/assign` or directly in Keycloak.

3. **Send the request with a comma‑separated `X‑Tenant‑ID` header** containing the opaque UUIDs of the silos you want to write to:
   ```bash
   POST /api/harbours
   Authorization: Bearer <JWT>
   X‑Tenant‑ID: c2405520-499f-4dba-ade5-a0df39954a84, test‑uuid
   Content-Type: application/json

   { "Name":"Ocean Lanka", "Code":"PV-123-1", "Address":"Sample Address", "ContactNumber":"Sample ContactNumber", "Status":"Sample Status" }
   ```

   The `TenantMiddleware` resolves each UUID, stores the list in the Gin context, and the outbox worker replicates the mutation to **both** `harbour_a` and `harbour_b`.

4. **Observe the logs** – you will see a `[LOG] … using DB: harbour_a` and a `[LOG] … using DB: harbour_b` line for the same request, plus outbox worker messages indicating successful replication.

This leverages the **Distributed Outbox (Saga Consistency)** already generated (see section 4). No additional code changes are required beyond the `@Federated` annotation and proper role assignment.

## 🛠️ Verification and Troubleshooting Logs

If you suspect database routing is going to the wrong database (such as the default/fallback database):
1. Enable debug logs inside `middleware/jwt_middleware.go` and `middleware/tenant_middleware.go`.
2. Look for stdout outputs on request handling:
   * `DEBUG JWTMiddleware: parsed roles = [...]`
   * `DEBUG TenantMiddleware: lowerRoles = [...], requestedTenants = [...]`
3. Compare the parsed roles list with your `tenant_roles` database registrations to ensure matches exist.
